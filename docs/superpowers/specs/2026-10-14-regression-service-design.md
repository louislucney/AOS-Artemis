# 回归服务设计（AOS × ARTEMIS）

- 日期：2026-10-14
- 状态：设计稿 v1.1（brainstorm＋两轮评审完成，待 Louis 审阅 → 转 Jira 工单 → 实施时同步 DESIGN.md）
- 背景：AOS × ARTEMIS MCP 服务（Node/TS）已具备测试闭环：用例生成（`figma_generate_tests`）→ 执行（`mobile_run_task` / `suite run`）→ 取证（轨迹/截图/崩溃）→ 报告（run-report xlsx + JUnit）→ 批次清单（`.artemis/design/runs/`）。缺口：**"回归"还不是一等服务**。
- 界面草图：会话视觉稿（`.superpowers/brainstorm/…`，不入库）；本文为准。
- 落地约束：实现走 Jira 工单；架构定论同步 `DESIGN.md`；测试不依赖真实 PG / 设备 / 外网（pg-mem、假 runner/子进程）。

## 1. 意图与为什么

现状的四个缺口（"翻旧账"时卡住的地方）：

1. **用例被覆盖**：三件套固定路径（`.artemis/design/tests.json|md|xlsx`），每次重新生成即覆盖，历史版本不留档。
2. **历史只存结果不存用例**：批次清单存 caseId/状态/失败域，**不存用例正文与 taskDesc**——过去那套用例无法原样重现。
3. **无跨次对比**：面板有通过率趋势，但没有"本次 vs 上次"的逐用例结论（修复/回归/新增/消失）。
4. **失败无归因记录**：`classifyFailure` 只是运行期一次判定，未累计、未人工确认——"案例问题还是执行偏差"没有承载物。

目标（Why）：让 MCP 作为服务方主动支撑**回归**——这次测过的功能，下次回归时能找回用例、重跑、对比是否符合；失败能定位 root cause；测试人员能在网页上介入裁决；数据"有据可依"，且这条路持续可演进。

## 2. 目标 / 非目标 / 反目标

**目标（P1 必须）**

- G1 功能切份与命名：一稿多功能 → 生成时按功能拆"份"，文件名＝**时间＋功能**（功能名由 MCP 生成，不靠人输）。
- G2 归档与记录：用例集版本归档（磁盘）＋登记与结果入库（DB，按项目隔离）。
- G3 面板回归闭环：项目页 → 引用过往"份"（多份/一份）→ 生成回归任务 → 下发执行（默认双端 iOS＋Android）→ 结果回写。
- G4 对比与结果表：本次 vs 上次（修复/回归/新增/消失；跨端提示）；结果表命名与内容纳入功能维度。
- G5 归因与统计：每条失败可裁决（案例问题/执行偏差/应用缺陷/不确定）；统计按 功能→用例→归因 组织，服务"下一轮改哪里"。

**非目标（本设计不做）**

- 不替 MCP 客户端自动执行（协议边界：客户端调服务端，不能反向命令客户端跑任务）。
- 不以"中心直连远程设备"为主路径（设备在项目机旁最优；既有 `deviceHosts` 保留为旁路能力，不动）。
- v1 不做权限/账号（内网假设，风险在文末标注）；不做定时调度（P3 候选）。
- 不做 DB/磁盘的自动清理动作（沿用仓库"保留期只读先行"口径）。

**反目标（做出来也算失败）**

- 破坏现有三件套门禁、批次清单、run-report 契约（只能增量演进）。
- 记录进 DB 后与磁盘产物漂移、对不上（DB 是索引，磁盘是事实源）。
- "功能名"变成人工必填（违背服务意识）。

## 3. 来自讨论的定论（Louis 拍板）

- 目标口径："提高运营效率、有据可依、方便定位问题"；回归：测过→下次能找回用例、重跑、对比。
- 网页有"回归引用"引导；引用单位为**份**，可"多份或一份"。
- 多项目接入：数据与保存路径按项目区分（沿用各项目 `.artemis/` 约定）。
- Excel 命名以"时间＋测试功能"为主；**功能名由 MCP 生成**。
- 记录入库：接受"登记进 DB、大件（用例正文/结果表/证据）留磁盘"的分工。
- 统计需要：成功/失败统计；两个目的——①方便测试人员介入 ②定位 root cause（案例有问题 vs 执行偏差）；持续演进。
- 大面板：多项目 → 点入项目 → 测试记录（成功/失败）→ 回归功能（引用过往测试文件 → 生成任务 → 下发执行）。
- 拓扑：设备**散在各项目自己的机器上**；中心与项目机**网络互通**；通常每项目 1 台 iOS ＋ 1 台 Android。
- 归因范围：**每条失败都能裁决**。
- 现实：**一份设计稿经常横跨好几个功能**。

## 4. 名词

- **设计源**：Figma 文件（fileKey）或 `.pen` 文件。
- **用例集批次（case-set）**：一次 `figma_generate_tests` 的产物；含来源、时间、指纹。
- **功能段（feature）**：批次内按功能切出的用例子集；**"份"＝功能段**（引用与命名单位）。
- **回归任务（regression task）**：面板上生成的任务——引用若干功能段＋目标端＋基线策略。
- **运行批次（suite run）**：一次实际执行（按端各一条），结果/证据/清单的载体。
- **裁决（verdict）**：测试人员对单条失败的归因结论。
- **项目机 runner**：项目机上的常驻执行者（心跳＋领任务＋本地执行＋回写）。

## 5. 设计

### 5.1 功能切分与命名（生成时）

切分信号（优先级从高到低，**确定性子优先**）：

1. **现成组织**：Figma Page/Section 名、pen 的 Flow 标注与画板排布（本仓库已有消费 `Flow/*` 标注与画板推断的先例）。
2. **屏幕命名归并**：按屏幕名公共前缀/关键词（"登录-*" → 登录）。
3. **流程聚类**：流程图连通子图/切点（跨功能边如"登录→首页"为切缝）。
4. **LLM 提炼**：active LLM 可用时，把该段屏幕清单交给它起短名（≤8 字，如"登录流程"）；不可用/失败 → 命名回退链（切分信号自带名 → 屏幕公共前缀词 → "功能N" 批次内序号并标注待复核），不阻断。
5. **回退**：切不出来 → 整批一份，名＝设计稿名（Figma 文件名随既有文件请求可取；pen 取 `.pen` 文件名）。

输出与命名：

- 每个用例带 `feature` 标签；批次含 `features[]`（功能名、用例数、涉及屏幕）。
- 产物主名：`<时间戳>_<功能>`；时间戳沿用现有 UTC 紧凑格式（与 runId/报告一致，展示层转本地）。
- **三件套同名配对是硬约束**（`suite check` 按 `json` 名找同名 `xlsx`）：一份功能段＝`<主名>.json/.md/.xlsx`。
- 功能名生成后**冻结**（改名不改历史档案；后续合并走别名映射，仿现有 i18n key 冻结模式）。
- **功能身份跨生成继承（P1 必做，否则统计在第一次重生成就碎）**：功能身份＝稳定 feature key（名称随 key 冻结）；重新生成时按**屏幕集合重叠**与既有功能自动匹配（确定性阈值规则），命中 → 继承 key 与名；低置信 → 记为 new key 并在批次内提示（人工对账确认，不静默合并）；人工合并/改名的别名映射文件为最小接口（P1 预留）。
- 结果表：`<时间戳>_<功能>_回归.xlsx`；多功能任务用引用主名合成（如"多功能N项"，细节留实现）。

### 5.2 归档（磁盘；事实源）

- 新增 `.artemis/design/case-sets/`：平铺 `<主名>.json|md|xlsx`（功能段三件套），meta（来源/时间/功能/覆盖摘要）并入 JSON 顶层（复用现有 harness 结构）。
- **live 兼容**：继续写 `.artemis/design/tests.json|md|xlsx`（全批合并、含 feature 标签）——`suite run`/`suite check` 默认路径与门禁不破。
- 既有 `runs/`（批次清单）与 `reports/`（结果表/JUnit）保留；增量字段：
  - run 清单增 `features`、`caseSetRefs`（来源批次/功能段）；
  - 结果表加"功能""端"列。
- 保留期：`suite retention` 增 `case-sets` 分类（只读报告先行，不自动删）。
- **冷启动**：历史 runs/ 清单**不回填**（缺 feature/端等维度，口径不齐）；趋势、基线与统计自新数据起算（回填另立）。

### 5.3 记录（DB；索引＋结果）

PG（沿用既有 store 模式：迁移、pg-mem 可测、不可用降级内存并如实标注）：

- `case_sets`：id、project_id、创建时间、来源（figma:<fileKey>/pen:<path>）、设计稿名、指纹、主名。
- `case_set_features`：case_set_id、功能名、用例数、屏幕（json）、json/md/xlsx 路径。
- `suite_runs`：id、project_id、触发来源（panel/cli/ci）、regression_task_id、引用（case_set/功能段）、端（android|ios）、设备、**执行机/产出方（runner；P1 手动运行填 hostname，P2 填 runner 名）**、**被测应用版本/构建号（app_version）**、状态、起止、计数（总/通过/失败/flaky/隔离）、失败域分布、门禁/退出码、清单与报告路径、对比摘要（json）。
- `suite_run_cases`：run_id、case_id、feature、端、状态、trace_id、失败域＋置信度＋理由、耗时、证据路径、重试/隔离、**裁决**（类型/裁决人/时间/备注）。
- `regression_tasks`：id、project_id、创建人/时间、引用（功能段列表）、目标端、基线策略、状态机、runner、产出 run ids。
- `runners`：id、project_id、机器名、最后心跳、在线、设备清单（端/名称/序列/状态）。

对比：默认按需求从 `suite_run_cases` 历史计算；摘要写入 `suite_runs.comparison`（展示稳定，细节可算）。保留期沿用只读报告口径，清理动作后置。

- **P1 访问路径（已确认 2026-10-14：直连中心 PG）**：各项目机 AOS 实例**直连中心 PG**（`MOBILE_TESTING_DATABASE_URL` 指向局域网中心库）——登记自然汇聚、零新代码（既有 store 模式）；不可用时沿用降级（内存＋如实标注；磁盘产物仍是事实源，可回填）。备选"汇聚 API"未启用（仅当安全否决 PG 暴露时改用）。**依赖升级声明**：中心 PG 成为聚合面单点——不可用时面板聚合/任务创建/裁决停摆，各项目本地执行不受影响（降级登记），恢复后可回填；备份与迁移需安排窗口（运维要求，见 §8）。
- **降级与回填**：DB 不可用 → 内存＋如实标注（运行产物仍在磁盘，不丢）；**回填＝只读扫描命令**（从 case-sets/runs 产物幂等重建登记，形态留实现）。**屏 A 数据源＝DB**（漏登记经回填修复；磁盘扫描兜底仅本机面板可选）。

### 5.4 面板（只读层与动作层分离）

现状：`/panel` 严格只读（无子进程/无网络/无写盘）——**保持**；新增"动作层"（新路由/API＋面板交互）承载选取/提交/触发。v1 内网无鉴权（风险标注）。**动作层前提重申**：引入写面后，内网任何人可创建回归任务与提交裁决（P2 后含触发执行）——结论仍为"接受"（内网假设），保留 `AOS_PANEL_ACTIONS=0` 兜底开关，风险在 README/DESIGN 标注。

- **部署拓扑（补）**：动作层与只读面板**同机部署在中心**；项目机产物（证据/结果表）P1 在中心侧**只显示路径**（项目机本地可打开，如实标注"产物在项目机"）；P2 随 runner 增**只读产物路由**（中心经项目机预览），再启用内联查看。

- **新屏 A 回归引用**：列出 case-sets 的功能段（时间＋功能名、用例数、最近通过率、来源）→ 勾"多份或一份" → 选端 → 生成回归任务（基线默认同份最近一次，见 §5.6）。
- **新屏 B 任务下发/执行**：任务状态机（统一定义见 §5.5：待执行→（P2 增"已领取"）→执行中→已回写/部分失败）；项目机/设备选择（runner 心跳清单，P2）；双端各自进度；结果回写摘要（分端通过/失败、失败域、对比上次、跨端提示）与产物链接（P1 路径展示）。
- **新屏 C 归因队列**：列表（初判＋端＋批次）→ 展开（摘要/理由/证据）→ 裁决（案例问题/执行偏差/应用缺陷/不确定）＋备注；动作（重跑本条、隔离）**P1 为执行指引**（给出对应命令，人在项目机执行），P2 接项目机通道后变真动作；支持同类批量。
- **增强 D 统计下钻**：项目→功能→用例；通过率/趋势/连败/flaky/归因构成；改进出口（生成反馈、环境清单、Jira）。
- L1 大面板与 L2/L3 批次页沿用现有实现，微调（功能维度、回归入口）。

### 5.5 下发与执行（项目机 runner）

- 主路径＝**项目机本地 runner**（设备在旁最优；模拟器限执行机本机，天然满足）：
  - 常驻进程（CLI 新子命令/守护），**心跳**：在线＋设备清单（adb/idb/Appium 状态）。
  - 通道（设计选择）：中心置任务为"待领取"，**runner 心跳时领取**——出站即可，免入站端口/防火墙配置；离线任务停留队列，上线自动继续。
  - 执行：复用 `suite-runner`（逐例：复位→提交→轮询→分类）；双端＝按端两个子运行，结果分别登记。
  - 回写：中心库登记；产物流本地（runs/reports/case-sets），中心按路径引用展示（P1 路径展示、不内联预览，见 §5.4 部署拓扑）；磁盘不可达时沿用"仅台账"降级。
- 协议边界：不做"中心推给 MCP 客户端执行"的路径；对话侧触发照旧（客户端调工具）。
- **任务执行契约（P1 手动路径与 P2 自动路径同一契约）**：
  - 面板生成回归任务 → 落库"待执行"；P1 由人在项目机执行 `suite run --task <id>`（名称留实现）——CLI 从中心库解析引用（功能段列表＋目标端），**展开为子运行：以该份的存档 JSON（已是子集）× 端逐个跑**（`suite run --tests <份文件>`）；跨份引用出现相同 caseId（内容一致）时去重只跑一次；不合并文档（避免跨批 id/覆盖语义纠缠）。
  - 子运行沿用现有 suite-runner；登记时带 `regression_task_id`；**任务状态机（统一定义）：待执行 →（P2: 已领取）→ 执行中 → 已回写 / 部分失败**（P1 手动路径无"领取"态）。**允许重复执行**：同一任务可再跑，追加新 runs（历史保留，任务页按次展示对比）。
  - **登记口径**：所有 suite 运行（panel/CLI/CI 触发）都登记 `suite_runs`；回归任务只是关联（nullable）。
  - P2 的 runner 只是把"人在项目机手动跑"换成"自动领取并执行"——契约不变。
- 备选（不做主路径）：中心经 `deviceHosts` 直连远程设备（既有能力保留）。

### 5.6 对比与结果表

- 口径：按端、按功能段；**默认基线＝同一功能段（份）的最近一次运行**（可指定；**解析键＝（case_set ＋ 功能段），禁止以 feature key 单独解析**——feature key 跨份连续，单独解析会把同功能的跨代运行混入）。理由：caseId 为内容哈希（`case-<sha12>`＝name+screens+steps），同份重跑稳定、跨生成会漂移——跨份对比会退化成"新增失败+消失"噪音，**显式后置**（需 case 匹配启发式）。该份无历史运行 → 首跑建立基准（显示"基准建立"）。分类：仍通过/修复/回归/新增失败/消失。
- 输出：任务页摘要＋结果表（加"功能""端"列；命名见 5.1）；JUnit 增量标注（实现定）。
- 跨端提示：同用例两端结果不同 → 疑似平台差异（归因线索）。

### 5.7 归因与改进闭环

- 初判＝现有 `classifyFailure`（域＋置信度＋理由），呈现给人；**每条失败可裁决**（范围定论）。
- 裁决写 `suite_run_cases.verdict`；同类（同域同因）批量。
- 三个出口：
  - 案例问题 → 生成反馈（扩展 `suite feedback`，按功能累计建议；**载体＝从 DB 裁决记录按需计算（无新存储）**；下一轮人工触发生成——仿 reconciliation"未裁决不升权"精神，不静默自动改）；
  - 执行偏差 → 环境改进清单（导出/视图）；
  - 应用缺陷 → Jira 建单（既有 jira 客户端；证据可 `jira_evidence_post`）。
- 隔离沿用现有 quarantine（owner 签字；**P1 面板给执行指引、不写盘**，P2 经项目机通道接入，不自动化）。

### 5.8 统计口径

- 维度：项目→功能→用例；时间窗：最近 N 批 / 近 10 次 / 近 7 天（实现统一）。
- 指标：通过率、趋势、连败、flaky（复用 flake 语义）、归因构成、失败域分布、跨端差异。
- 来源：DB；证据顺路径看磁盘。服务对象：测试人员（裁决/改进）、负责人（趋势）。
- **血统语义（补）**：feature 级指标跨份连续（靠 feature key 继承）；case 级指标（连败/flaky/归因构成）只在**同份**重跑内累计——跨份不做 caseId 聚合（避免失真）；跨份连续性由 feature 维度桥接。

## 6. 兼容与约束
